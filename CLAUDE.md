# Noxen

Drone frame parts, each generated by the topology engine in `topo/` from one script. GitHub Actions runs every
optimisation; the page at the repo's GitHub Pages URL always shows the current assembly.

## Commands
```
python -m topo.run parts/<name> --h 2.0 --maxit 10 --no-coarse   # 2-minute smoke to see the setup load (never a full run here)
python tools/solid_check.py parts/<name>/part.stl                 # the only gate (CI runs it)
python tools/dim.py <section>                                     # one section of systems/dimensions.md, never the whole file
python tools/sweep.py [--apply]                                   # the Monday sweep (scheduled task, fresh session): the only housekeeping
```

## Sessions (Spark 9 Nov: the design chat is always free, and usage stays low)
- The design chat is the session Spark talks to. It answers, decides, writes Spark's notes to `parts/<part>/feedback.md`, and hands everything that waits (a smoke, the test suite, a run, a check-in) to a worker. It does small work itself (a question, a one-file edit with no run). It wakes only for Spark and for a worker's report: no check-ins, no polling, no background jobs in it.
- A worker is `create_session` on this repo, one per stream (a part family, a study, an engine change), never one per part. The prompt names the parts, the goal, the `feedback.md` files to read and the design chat's session id; it points at files, never pastes them; this file applies there. At most 3 live workers per design chat and one engine worker in all; before starting one, archive your finished workers. Spark's "rerun <part>" or "<part>: <notes>" (notes to `feedback.md` first) goes to the stream's live worker (send_message), else a new one.
- A worker runs the loop below alone (Spark 9 Nov: "make these choices yourself, should never be asking them from me"): it fixes each fail at its root cause by whatever the design needs (room, cuts, sockets, budgets, splitting a part, adding nodes) until every part passes or it is blocked on what only Spark has (a measurement, a purchase). It never loosens a gate (`max_worst`, the solid check, the audit), never changes what a part is for, never calls a part accepted; it reports what it changed as done, never as a question.
- Done: the worker publishes the artifact, sends the design chat ONE message (send_message, at most 10 lines: per part PASS/FAIL, mass g, worst index and case, what it changed and why; the artifact link), then archives itself (archive_session, its own id). The design chat on it: `git pull -q`, sends Spark each new `preview.png` (SendUserFile) with those lines, archives the worker if still live. Nothing reaches Spark in between.

## The loop (a worker)
- Write or edit `parts/<name>/part.py`: `setup(h) -> Part` and `SPEC = dict(h=..., gen_cm3=..., max_worst=0.5)`. Pattern: `parts/motor_mount/part.py` (small), `parts/hub_deck/part.py` (large, with `inputs/`). The run refuses a grid over 300k cells at the SPEC h (the smoke prints it; over that the solver falls to multigrid and never converges): coarsen h or trim the envelope. Give the part a line in `systems/<drone>.assembly.json` (id = folder name, placeholder shape, pose).
- `git pull --rebase`, touch only your own parts, commit, push to main. The push starts the runs (every session push is under Spark's account): never dispatch after a push, it runs the parts twice (9 Nov). Dispatch only a rerun with no setup change: `gh api -X POST repos/sparkiscool/noxen/actions/workflows/parts.yml/dispatches -f ref=main -f 'inputs[parts]=<names>'`. A running part whose setup changed on main stops itself within 3 min and the new one runs (Spark 29 Oct). CI runs the engine, commits `result.json` + `part.stl`, rebuilds the page.
- To fix or change a part: read `parts/<name>/feedback.md` (Spark's notes) and `parts/<name>/result.json` (solid check, worst index, mass). Nothing else.
- A failed gate or strength index is a class of setup, not one part (Spark, 28 Oct): name the cause, add the check to `topo/audit.py` (with a `test_topo` case) that would have refused this setup before the run, apply the fix to every part that shares the cause, then push. Fixing only the part is a patch and the fail comes back.

## Setup audit (runs before every solve, `topo/audit.py`)
A run refuses to start when: drawn solid is over 30 % of the part; one drawn body holds over 60 % of the drawn
material with a thick core (a drawn structure); any drawn body has a core over 8 mm away from every hole and face (a
block); a loaded drawn body has less than one member of design room behind it; a drawn body is under 2.5 mm across its
smallest extent after its cuts, or has a wall under 2 mm anywhere after them (the gate erodes it; a 2.0 collar with 0.5 resin
grooves is 1.5 at the grooves, 7 Nov; thin_ok for the camera posts); a loaded drawn body reaches the support only
through room thinner than a member (a slab or a stub: the engine bridges it with a blob on a neck); a load region reaches off its
drawn face into room (the engine grows a knob out to the loaded nodes); the room filled solid fails `max_worst` (no layout in it can pass: open the room along the load path, 9 Nov). The fix is always the setup, never a
`--set audit=warn`: delete the block, open the envelope behind the feature, move the cut. `result.json` carries the
audit report; `python -m topo.run parts/<name> --h <SPEC h> --maxit 1 --no-coarse` runs it in a minute (at the SPEC h: room is measured
in cells, a coarser h can pass a setup the run refuses).

## Never
- Run a full optimisation in a session. Never read meshes as text, logs or `inputs/`. Always look at what Spark looks at (Spark 7 Nov: "you should always be looking at the same artifact as me"): every new result's `parts/<name>/preview.png`, and the page itself rendered with the headless browser, before reporting it or judging a shape.
- Edit `topo/` in a part worker, except the audit check a failure calls for. Other engine changes go to the engine worker (`python -m topo.test_topo` in it, and `python3 tools/predict.py --engine <new tag>` in its commit so old timings are ignored); Spark never pastes a prompt (Spark 29 Oct).
- Patch a failed run by drawing more solid. Fix the setup: room, cuts, loads, volume.

## Design rules
- Draw only attachments: pads, bosses, socket walls, seats, contact faces, and the gusset into the body. Everything between them is generated.
- Cut bolts, nuts, rods and tool sweeps through the whole envelope, not just to the pad.
- Supports are the faces it really bolts to. Loads are the masses it carries at their CG plus the joint reactions from the system, each as its own case (flight, crash, handling). No guessed loads: if a case is missing, say so.
- PCTG for every printed part (Spark 8 Nov, was PETG: 10-20x the impact toughness at 90 % of the stiffness, PETG settings +10 C; the nodes and arms broke in testing; `topo/material.py` PCTG, E numbers until a coupon), TPU 95A feet, nothing under 2 mm (one exception: the camera M2 insert posts, Ø5.6 round Ø3.2, 1.2 wall, Spark 29 Oct by coupon), 3 mm and 6 mm carbon only (socket bores 3.2 / 6.2, every socket with a Ø2.5 resin injection port (one 14 G blunt tip, Spark 8 Nov) 1.5 above its floor out between the members and three 0.3 resin pockets along the bore the port feeds: `cage_node_lib.port_cut` / `socket_cuts(pockets=3)`, Spark 5 and 7 Nov), Bambu A1 mini 180 cube, largest flat face down.
- Numbers come from `systems/dimensions.md`, tagged M measured, C CAD, E estimate. Every bought part is proposed with an Amazon listing (Spark 29 Oct: "everything needs to be on Amazon"); a part only a distributor sells is named as the fallback, never the proposal.

## Runs and check-ins (a worker's)
- Local jobs over a minute (smokes, the test suite, recuts) run in the background; the turn ends with a line on what is running. After a push: `python3 tools/predict.py <parts>` prints the latest predicted finish and a check-in delay. Schedule ONE check-in into the worker itself for then (send_later, message "check runs: <parts>") and end the turn. No polling, no waiting, check-ins never under an hour apart. Every time Spark reads is Pacific (Seattle), never UTC.
- A check-in turn: `git pull -q`; for each part whose `result.json` changed (new `part_sha`), look at its `preview.png` and the page; a fail goes back through the loop. Then `python tools/build_site.py --inline` and publish `site/<drone>.html` at the `artifact` URL in `systems/<drone>.assembly.json` (the drone's one artifact, every current part; a new drone's first publish writes its URL there). A part not done: `predict.py --started <run start>` and one more check-in. Every part done or blocked: report and archive (Sessions). Read nothing else.

## Adding to the workflow (Spark, 28 Oct)
A new rule or feature is merged into the process, never stacked on top of it. In order of preference:
1. Code, where it can be: a check in `topo/audit.py`, a gate in `topo/run.py`, a step in `parts.yml`. It runs every time without anyone remembering it.
2. A change to an existing line here, when it only guides what a session writes.
3. A new line here only when neither fits, and only after reading this file to see what it replaces.
Every addition removes or replaces whatever it supersedes. This file stays under 60 lines; a session that would push it over moves something into code first. No rulebooks, no docs folder, no agents or skills that restate rules.
