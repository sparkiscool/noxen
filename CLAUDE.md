# Noxen

Drone frame parts, each generated by the topology engine in `topo/` from one script. GitHub Actions runs every
optimisation; the page at the repo's GitHub Pages URL always shows the current assembly.

## Commands
```
python -m topo.run parts/<name> --h 2.0 --maxit 10 --no-coarse   # 2-minute smoke to see the setup load (never a full run here)
python tools/solid_check.py parts/<name>/part.stl                 # the only gate (CI runs it)
python tools/dim.py <section>                                     # one section of systems/dimensions.md, never the whole file
```

## What you do in a part session
- Write or edit `parts/<name>/part.py`: `setup(h) -> Part` and `SPEC = dict(h=..., gen_cm3=..., max_worst=0.5)`. Pattern: `parts/motor_mount/part.py` (small), `parts/hub_deck/part.py` (large, with `inputs/`). The run refuses a grid over 300k cells at the SPEC h (the smoke prints it; over that the solver falls to multigrid and never converges): coarsen h or trim the envelope.
- Give the part a line in `systems/<drone>.assembly.json` (id = folder name, placeholder shape, pose).
- Commit, push to main. A push with Spark's credentials starts the runs; one with the app token does not, so always then: `gh api -X POST repos/sparkiscool/noxen/actions/workflows/parts.yml/dispatches -f ref=main -f 'inputs[parts]=<names>'` (a part already running on the same setup is skipped; a running part whose setup changed on main stops itself within 3 min and the new one runs, so an old design never finishes: Spark 29 Oct). Stop. CI runs the engine, commits `result.json` + `part.stl`, rebuilds the page.
- To fix or change a part: read `parts/<name>/feedback.md` (Spark's notes from the page) and `parts/<name>/result.json` (solid check, worst index, mass). Nothing else.
- A failed gate or strength index is a class of setup, not one part (Spark, 28 Oct): name the cause, add the check to `topo/audit.py` (with a `test_topo` case) that would have refused this setup before the run, apply the fix to every part that shares the cause, then push. Fixing only the part is a patch and the fail comes back.
- Never rerun or re-version a part on your own, except in auto mode (below). Spark reviews every result on the page and asks for the next step.

## Setup audit (runs before every solve, `topo/audit.py`)
A run refuses to start when: drawn solid is over 30 % of the part; one drawn body holds over 60 % of the drawn
material with a thick core (a drawn structure); any drawn body has a core over 8 mm away from every hole and face (a
block); a loaded drawn body has less than one member of design room behind it. The fix is always the setup, never a
`--set audit=warn`: delete the block, open the envelope behind the feature, move the cut. `result.json` carries the
audit report; `python -m topo.run parts/<name> --h 2.5 --maxit 2 --no-coarse` runs it in a minute.

## Never
- Run a full optimisation in a session. Never read meshes, logs, images or `inputs/`.
- Edit `topo/` in a part session, except the audit check a failure calls for. Other engine changes are their own session, which THIS session starts itself (`create_session` on the repo, the whole brief in the prompt, `python -m topo.test_topo` in it); Spark never pastes a prompt (Spark 29 Oct).
- Patch a failed run by drawing more solid. Fix the setup: room, cuts, loads, volume.

## Design rules
- Draw only attachments: pads, bosses, socket walls, seats, contact faces, and the gusset into the body. Everything between them is generated.
- Cut bolts, nuts, rods and tool sweeps through the whole envelope, not just to the pad.
- Supports are the faces it really bolts to. Loads are the masses it carries at their CG plus the joint reactions from the system, each as its own case (flight, crash, handling). No guessed loads: if a case is missing, say so.
- PETG, nothing under 2 mm, 3 mm and 6 mm carbon only (socket bores 3.2 / 6.2), Bambu A1 mini 180 cube, largest flat face down.
- Numbers come from `systems/dimensions.md`, tagged M measured, C CAD, E estimate.

## Runs and check-ins (how Spark hears about results)
- One session does the whole batch itself: no subagents, no side sessions (the engine runs on GitHub, setups are cheap to write). Local jobs over a minute (smokes, the test suite, recuts) run in the background and the turn ends with a line on what is running, so Spark can keep talking (Spark 29 Oct). It reports once per batch, at the check-in, with the artifact republished; nothing in between. Runs start only from a design session's push or a rerun Spark asked for. After starting one: `python3 tools/predict.py <parts>` prints one line with the latest predicted finish and a check-in delay. Schedule ONE check-in for then with send_later (message: "check runs: <parts>"), then end the turn. No polling, no waiting. Every time Spark reads is Pacific (Seattle), never UTC.
- A check-in turn: `git pull -q`; for each part, if `parts/<part>/result.json` changed (new `part_sha`) send Spark `parts/<part>/preview.png` with SendUserFile and one line: PASS/FAIL, mass g, worst index and case, minutes; link https://sparkiscool.github.io/noxen/. Then `python tools/build_site.py --inline` and publish `site/<drone>.html` at the `artifact` URL in `systems/<drone>.assembly.json` (the drone's one artifact, every current part; a new drone's first publish writes its URL there). If a part is not done: rerun `predict.py --started <run start>` and schedule one more check-in. Read nothing else.
- Operator mode (default): Spark makes every choice; the session reports and proposes. Auto mode (Spark says so, or that they are going to bed): the session keeps the batch going alone until Spark is back, check-in by check-in, and reports once in the morning with the artifact republished. On its own it may: fix a part that failed the audit, the gate or the budget (root cause first, as above) and rerun it; trim an envelope or coarsen `h` for a part that hit the 5.5 h cap twice and rerun; cancel a doubled run; reschedule the check-in. It may not: change what a part is for or how it attaches, add or drop rods or nodes, loosen a budget or a gate, or call a part accepted. Anything it would have asked goes in the morning report instead. Usage: each check-in re-reads the conversation, so check-ins are spaced at the predicted finish, not more often, and never under an hour apart.
- Engine change (`topo/` edited): `python3 tools/predict.py --engine <new tag>` in that commit, so old timings are ignored.
- Spark's reply in that session: "rerun <part>" dispatches `parts.yml` for it; "<part>: <notes>" goes to `parts/<part>/feedback.md`, then the fix per "What you do in a part session". Then predict and schedule the check-in again.

## Adding to the workflow (Spark, 28 Oct)
A new rule or feature is merged into the process, never stacked on top of it. In order of preference:
1. Code, where it can be: a check in `topo/audit.py`, a gate in `topo/run.py`, a step in `parts.yml`. It runs every time without anyone remembering it.
2. A change to an existing line here, when it only guides what a session writes.
3. A new line here only when neither fits, and only after reading this file to see what it replaces.
Every addition removes or replaces whatever it supersedes. This file stays under 60 lines; a session that would push it over moves something into code first. No rulebooks, no docs folder, no agents or skills that restate rules.
